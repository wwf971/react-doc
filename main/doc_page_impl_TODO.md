# TODO

What the design of the page leaves for later, in one place. The design documents (`doc_page_impl_xxx.md`) describe what exists; where something is missing they say so in a short line and point here, so a missing feature is written down once, with its reasons, and not scattered as notes through the documents.

How the list is kept (also in `AGENTS.md`):

- An item says **what is missing**, **why it would matter** and **what already exists to start from**, with a link to the section of the design document it belongs to. It does not hold a plan of work.
- When a request matches an item, the agent says so and asks the user to confirm that the item is what they mean before building it.
- After the work, an item that is fully done is **removed**, and its design goes into the design document as the description of what exists; an item partly done is **rewritten** to say what is still missing.
- A new gap found while working is added here, under the functional group it belongs to, instead of a TODO paragraph in a design document.

## Packages

- <a id="package-registry-import"></a>**Importing node kinds between registries.** A diagram component of a package has one fixed node registry, written in code ([Node Registries](../package/cloud-dev-vis/doc/card-diagram-impl.md#node-registries)); a combination of kinds of two series (Power Platform cards beside the cards of another platform in one diagram, a doc page adding a kind of its own) is a registry written in code today. A mechanism declaring a combination in data, per component type or per block, would make that a configuration. The registry mechanism (`nodeRegistryBuild`) and the kinds as values are the place to start.
- <a id="package-source"></a>**Packages with a version.** A package is named by its folder or by a name found in folders and `node_modules/` ([importing packages](doc_page_impl_package.md#importing-packages)); a package from a registry or a git repository, with a version checked, would need a resolver beside `docPackageDirFind`.
- <a id="package-writable"></a>**Editing a package from the page while developing it.** A package treated as a doc page is read-only with no exception, so the visual editors cannot be tried in its own documents: its author edits its files in an editor. A launch option making one package writable (`react-doc dev --package-writable`) would be the one exception, deciding in `DocPageLoaded.isReadOnly`.
- <a id="package-backend-config"></a>**Packages of a backend started alone.** The service backend learns the packages from the page's sync; its own config (`service-backend.yaml`) names doc pages but no packages, so a backend started without the page does not see their templates.
- <a id="package-dependency-collect-reload"></a>**Reloading a dependency extractor.** The extractors manifests name (`dependencyCollect`) are loaded when the configuration is resolved; a new or changed one needs a restart of the development server ([Components of a doc page](doc_page_impl_mdx_comp.md#components-of-a-doc-page)).

## Command line

- <a id="cli-create"></a>**`npm create`.** `react-doc pack` stages the published package and the installed mode serves from it ([Two modes](doc_page_impl_cli.md#two-modes-a-checkout-an-installed-package)); a thin `create-react-doc` package would let `npm create react-doc@latest my-docs` work as `npm create vite` does, only calling `react-doc init workspace`.
- <a id="cli-build"></a>**Building from the command line.** `react-doc dev` serves a folder; `react-doc build <path> --out <dir>` would make the static build of the same target with the same launch layer ([The launch layer](doc_page_impl_cli.md#the-launch-layer)), so a doc page lying anywhere deploys without a config file.

## Card diagram animation

- <a id="animation-visual-edit"></a>**A visual edit mode of an animation.** An animation is edited as its source ([Card Diagram Animation](../package/cloud-dev-vis/doc/comp-card-diagram-animation.md)). Editing the diagram with the framework's editor, and states and tracks from the control area, would be its visual mode; the diagram's part is `DiagramVisualEdit` on `document.diagram`.
- <a id="animation-scrub"></a>**Scrubbing.** The progress on a line shows where a transition is but cannot be dragged; everything is a function of the frame, so a drag would be `seekTo`.

## Settings panel

- <a id="settings-as-mdx"></a>**The settings panels as MDX documents.** The tabs of the settings panel are built in code from config items (`ConfigPanel`) and custom components (the Workspace graph, the Services tab). Written as MDX documents of a built-in doc page, with components for their parts, they would get everything a document has: blocks that open in the block popup, in-place editing, a layout an author changes without code. The Workspace graph already opens in the block popup through `BlockPopupSurface` with a `popupKey`, the step a block of such a document would take anyway.

## Config

- <a id="config-declaration-edit"></a>**Adding and removing config keys and declarations from the page.** The doc page layer edits a value a declaration already holds; adding a key to a declaration, removing one, and adding a declaration are written in the files ([The doc page layer](doc_page_impl_config.md#the-doc-page-layers)). The yaml utilities that insert and remove keys in place are the place to start ([YAML utilities](doc_page_impl_yaml_utils.md)).

## Editing

- <a id="edit-undo"></a>**Undo and redo.** Every write of the edit layer is already recorded with the texts before and after (`DocEditStore.historyRecord`, [History records](doc_page_impl_edit.md#history-records)); what is missing is the routes that write a record back (`historyUndoRequest` / `historyRedoRequest` through the router's `dispatch`, [Extending the layer](doc_page_impl_event.md#extending-the-layer)), refusing where the file is no longer the text after.

## Source

- <a id="source-file-rename"></a>**Renaming and moving a file from the page.** A file is created and deleted from the page ([creating and deleting files](doc_page_impl_source.md#creating-and-deleting-files)), but renamed or moved only on disk, where every link to it, every side-panel `doc` and every asset dependency naming it breaks. A rename from the page would rewrite those references in the same request. The link index of the development server (`plugin/doc-link-index.ts`: every reference of every document with its line, [Backlinks](doc_page_impl_nav_backlink.md#the-link-index)) already finds the documents and lines to rewrite, the side-panel nodes are found through `nodeSource`, and the file operations of `plugin/doc-source-file.ts` are where a rename with its rollback belongs.

## Events and component state

- <a id="event-subscription"></a>**Subscriptions by other subjects than a block.** The event layer delivers events to components at a place of a document (`subscribe` / `publish` of the router, keyed by document and block line; `placeReveal` of the backlinks, [Events delivered to components](doc_page_impl_event.md#events-delivered-to-components)). Missing: a subject that is not a block, so that a component is told when its asset object changes instead of asking (`assetRefreshRequest`, [Changes made by others](doc_page_impl_mdx_comp.md#changes-made-by-others): the asset service layer would publish on `doc-asset-change` with the object as subject), and the service events below with an instance as subject; one more key of the subscription and of the matching in `publish`.
- <a id="state-two-tabs"></a>**Component state across browser tabs.** Two browser tabs of one page keep separate state objects; keeping those of one key in step needs a channel (`BroadcastChannel`, a websocket), the one subscriptions would use; the key format is already the address ([Extending the layer](doc_page_impl_mdx_comp_state.md#extending-the-layer)).

## Asset service layer

- <a id="asset-remote-store"></a>**Remote stores and a local cache.** The page has one store, `local`; a remote store answering the same api over the network, and a local cache of it whose versions are never the truth, are planned, and references already name their store ([Stores, objects, versions](doc_page_impl_asset.md#stores-objects-versions)).

## Api registry

In the order they would matter ([Unified api registry](doc_page_impl_api.md)):

- <a id="api-registry"></a><a id="api-hotkey-client-map"></a>**Keys edited from the page.** The keyboard maps are files of the package, the doc pages and the workspace, and the host's; the reader can only pick a map of a doc page ([Where the maps are](doc_page_impl_api_hotkey.md#where-the-maps-are)). A client map kept in the browser above the stack, edited in the API tab (a key, an api chosen from the registry), would be the counterpart of the client config layer; `DocHotkeyStore.mapListStack` takes one more map.
- <a id="api-job"></a>**An api that is a job.** An api answers within the call ([Core concepts](doc_page_impl_api.md#core-concepts)); a long operation (a build, a scan of every document) has no form yet. The jobs of the service backend (`serviceJobGetRequest`, polled) are the model: an api returning a job id, and `api/jobGet` to follow it.
- <a id="api-remote-build"></a>**Remote calls without the development server.** A built page keeps its apis for the page's own ui only: the bridge is a route of the development server ([Remote callers](doc_page_impl_api.md#remote-callers)). A page served otherwise would need the same bridge in its server, with the authorization a page on the network needs (the question of [a deployed backend](#service-deployed-backend)).

## Object registry

<a id="object-registry"></a>In the order they would matter ([Objects and Types](doc_page_impl_obj.md)):

- <a id="object-registration-persistent"></a>**Persistent registrations and pins.** A registration lives in the memory of its registry (`registrationByRef` of the page, `registration_by_ref` of the backend) and is gone with a restart; a reference that someone holds for good (a group of a service naming a document, a timeline naming an asset) cannot ask the registry to keep tracking its identity and provider across restarts, nor be told it became `missing`. A pinned registration kept beside the backend config (as `service-kernel.yaml` keeps the routes), and the page registering the references its documents hold, are the place to start; the statuses already say registered from found.
- <a id="object-type-version"></a>**Versions and contracts of types.** A type has an id and no version: two templates extending `core.task` agree by declaration, and a change of what a type promises reaches every provider at once. A version in the id (`core.task@1`), assignability across compatible versions, and a check that a provider's answers keep the promise (the summary keys, the update it accepts) would make a type a contract; the [contract behind an infra name](#service-reference) is the same question for services.
- <a id="object-type-source"></a>**Types of doc pages and packages beyond their frontend objects.** Types come from the built-in file, the templates' scripts and the doc pages' `object-frontend.yaml`, which declares types below `frontend.object` only ([Frontend objects](doc_page_impl_obj_frontend.md#the-declarations-object-frontendyaml)); a doc page cannot declare a type for the objects of other providers (a `core.task` subtype its documents' groups use), and a package declares none (a package's `object-type/`), though their components can already be views (`expose.objectView`). The frontend object provider's `typeDefineGet` is the path such a declaration would take.
- <a id="object-relation-diagram"></a>**A diagram of relations.** A card diagram draws objects as nodes, but its lines are its own data; a diagram whose nodes and lines come from a relation query (the dependencies of the instances, the links of a part, the members of a group), laid out automatically, would show the registry's graph. The relation queries and `ObjectView` nodes are what it would be built from.
- <a id="object-backend-page"></a>**The backend asking the page.** A service finds the page's documents only as the page registered them (`registered`, possibly stale); it cannot resolve a section, read a document or follow a link. A route from the backend to the page's providers while a page is connected (the remote api channel of the development server, [Remote callers](doc_page_impl_api.md#remote-callers), is the model) would make the page a provider of the backend's registry.
- <a id="object-resolve-batch"></a>**Batched resolves and pushed changes.** Each object drawn resolves alone (a query primes its objects, so a list costs one request), and the page learns of a change of a backend object only by asking again after the provider's cacheSecond or a version change. Resolving the references of one render in one request, and the backend pushing `object_changed` to the page (the [subscriptions](#event-subscription) of the event layer), would cut both.
- <a id="object-search-line"></a>**Objects as the ends of a line.** The create panel of a card diagram adds an object as a node ([In a card diagram](doc_page_impl_obj_search.md#in-a-card-diagram)); the panel of a line does not search objects for its ends, nor does a line drawn from a relation of the registry exist. The search session the create panel uses is the part to reuse.
- <a id="object-search-index"></a>**An index for the search.** A search plans by the hosts, counts, and fetches a bounded page of each provider; a provider with many objects and no word it can filter by is counted, never searched inside. A provider-side search index (a full-text table of an instance, the page's search index of documents, `DocSourceStore.searchDocs`, for the headings) answering the words themselves would let a search find inside it; `count` and the pushed word are the protocol it would extend.
- <a id="object-backend-write"></a>**Creating and deleting the objects of a service.** The registry hands `create`, `delete`, `relationCreate` and `relationDelete` to the provider that owns what they change ([Writing through the registry](doc_page_impl_obj.md#writing-through-the-registry)), and the page's providers implement them (the frontend objects, the asset store); the backend's registry has `update` only, so a todo cannot be added through `object/create`, only through the instance's own apis. Object apis `objectCreate`, `objectDelete`, `relationCreate`, `relationDelete` of a script (`@object_api`, with `createTypeList` in `objectProvide`), the kernel's routes for them, and the peer provider passing them on are what is missing; the page's side is in place.
- <a id="object-update-authorization"></a>**Who may change an object.** An update goes through when the consumer allows it and the provider offers it; the user behind the change is not known to the provider ([Authorization](doc_page_impl_service_kernel.md#authorization)), and the page's providers offer no update at all (a section, a group written in a document are changed by editing the document). Updates of document objects through the edit layer, and the end user carried to a service provider, are both missing.

## Frontend objects

<a id="object-frontend"></a>What the [frontend object service layer](doc_page_impl_obj_frontend.md) leaves for later:

- <a id="object-frontend-store"></a>**Assets elsewhere than the doc page's default folder.** An object keeps its assets in the default asset folder of the doc page that lists it, in its group folder; an object whose assets lie in another folder, another doc page or a remote store ([Remote stores](#asset-remote-store)) is not created from the page, though the entry can list any object of the store and attach one. Moving an object (its line, its group folder) from one doc page to another is a step by hand.
- <a id="object-frontend-schema"></a>**What a type promises of its assets.** A type declares its modes, not the kinds of assets its objects hold nor their shape (a `book` has a title), so every mode reads the data defensively and a wrong asset is found only when drawn. A declaration of kinds with a schema in `typeList` (checked when an asset is created or written, shown in the settings tab) would make a type a contract; the [versions and contracts of types](#object-type-version) are the same question for the registry.
- <a id="object-frontend-version"></a>**An asset pinned to a version.** A frontend object reads the head of each of its assets: the entry lists `{ key, kind, objectId, name, pathList }`, no version ([Naming and finding the assets](doc_page_impl_obj_frontend.md#naming-and-finding-the-assets)). An object whose part must stay as it was while its asset is revised (a quotation of a document at a version, a released configuration) would list `versionId` beside the object id; the asset store already resolves a reference to a version (`refQuery` with `versionId`), and the mode api, the index and the writes of the entry are where it would be carried.
- <a id="object-frontend-change"></a>**Being told of a change.** A mode re-renders when the asset store hears of a change (the page's own write, a file changed on disk); a mode holding something derived (an engine, a draft) is not told which asset changed. The [subscriptions by other subjects than a block](#event-subscription), with the object as subject, are the channel it would use.

## Service layer

In the order they would matter ([Service layer](doc_page_impl_service.md)):

- <a id="service-reference"></a>**A rigorous reference to a service.** A service is referred to by a name string today ([Naming a service](doc_page_impl_service.md#naming-a-service)); its objects already have references and types of the [object registry](doc_page_impl_obj.md), which a contract of an infra name could be declared with. Missing: a **contract** behind an infra name (its apis and their versions, the storage type it promises), declared by the templates implementing it and checked when a dependency is resolved, so a consumer can require `sqlite@1` and the kernel can refuse a provider that does not implement it; and an **identity** of a template beyond its id and name: a content hash of its files at a version (computed when a version is recorded, so the backend also notices files changed without a new version) and a signature of its author, so an instance can prove what it was created from and a template from elsewhere can be trusted or refused.
- <a id="service-backup"></a>**Backup to another storage, and migration of a consumer's data.** A backup on the local disk exists: the `local-backup` infra service keeps a consumer's data as zip files in a folder ([The local-backup infra service](doc_page_impl_service_storage.md#the-local-backup-infra-service)). Missing: the `backup` storage operation to **another storage** (a cloud object store the backup infra would depend on, the zip files of local-backup being what is sent), with the backup status reported as part of the storage (last backup, verified, pending changes), since reliability is a state to observe, not a flag; a backup **scheduled** by the infra itself (a resident `run()`) instead of asked for by the consumer; and moving a consumer's database from one sqlite instance to another when a name is rerouted (a backup checked out into the other instance is the manual way today).
- <a id="service-data-clear"></a>**What a deleted instance's data becomes.** Deleting an instance keeps its folder (`.deleted-…`) and everything it had in infra services: its database in sqlite, its backups in local-backup, which lists them as orphans to delete by hand ([Lifecycle and hooks](doc_page_impl_service_kernel.md#lifecycle-and-hooks)). Missing: a policy, declared per infra service or chosen at the deletion (keep, remove, remove after a time), carried by the `onDestroy` hook or by the kernel asking every infra the instance depended on, so that nothing is removed by surprise and nothing is forgotten either; the orphan listing of local-backup and sqlite's `consumerList` are what such a policy would act on.
- <a id="service-log-audit"></a>**The audit and the backup of the logs.** An audit group (permissions changed, instances deleted, routes set) with a stricter retention than the operational records, and the backup of the log database through a storage infra once there is one to back up to ([The logging infra service](doc_page_impl_service_kernel.md#the-logging-infra-service)).
- <a id="service-permission"></a>**A policy of permissions.** Which caller may call what, which infra names an instance may add at runtime and with which scope, in one place, with the end user behind a page request carried through the calls and into the log's principal ([Authorization](doc_page_impl_service_kernel.md#authorization), [Dependencies](doc_page_impl_service_kernel.md#dependencies)).
- <a id="service-template-update"></a>**Comparing and updating from a template.** With the hash above, the Services tab could say which files of an instance differ from its template's version and from the template's current version; `Update from template` (copying chosen files again, the data kept) and `Recreate` would be explicit steps, never a template change reaching instances by itself; where a newer script needs another shape of data, the update carries a migration of the instance's state.
- <a id="service-template-from-instance"></a>**Templates from instances.** Saving an instance (its script and dashboards, not its data) as a new template, a fork with its own id and versions.
- <a id="service-deployed-backend"></a>**A deployed backend.** The backend on a server, reached by a built site or a development server alike by its address alone ([Reaching the backend](doc_page_impl_service_dashboard.md#reaching-the-backend)). It needs to be reachable from the page's origin (a reverse proxy on the site's origin, or CORS for the origins its config names; it sends no CORS headers on purpose today), its doc pages listed in its own config instead of the development server's sync, and the permissions above, since a page on the network is no longer the only caller. Its address would then come from `config.yaml` for a build too, not only from a host passing it.
- <a id="service-call-any-component"></a>**Calls from any component.** Only dashboards send `serviceApiCallRequest`; a component of the registry that is not a dashboard could call an instance by a target too, as the page does.
- <a id="service-isolation"></a>**Execution isolation.** Instances share one process; a template could declare how its instances run (the shared process, a worker, a process of their own, outside the backend), for scripts that are not trusted or need resources of their own; a hook that does not return could then be killed instead of recorded.
- <a id="service-event"></a>**Service events.** The lifecycle changes, the dependency changes and the log records share one envelope only in the log; a subscription (a dashboard told that its instance restarted, a service told that its dependency came back) would be the next channel beside the calls, on the [subscriptions](#event-subscription) of the event layer.
