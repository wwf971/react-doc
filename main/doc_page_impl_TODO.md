# TODO

What the design of the page leaves for later, in one place. The design documents (`doc_page_impl_xxx.md`) describe what exists; where something is missing they say so in a short line and point here, so a missing feature is written down once, with its reasons, and not scattered as notes through the documents.

How the list is kept (also in `AGENTS.md`):

- An item says **what is missing**, **why it would matter** and **what already exists to start from**, with a link to the section of the design document it belongs to. It does not hold a plan of work.
- When a request matches an item, the agent says so and asks the user to confirm that the item is what they mean before building it.
- After the work, an item that is fully done is **removed**, and its design goes into the design document as the description of what exists; an item partly done is **rewritten** to say what is still missing.
- A new gap found while working is added here, under the functional group it belongs to, instead of a TODO paragraph in a design document.

## Packages

- <a id="package-registry-import"></a>**Importing node kinds between registries.** A diagram component of a package has one fixed node registry, written in code ([Node Registries](../package/cloud-dev-vis/doc/card-diagram-impl.md#node-registries)); a combination of kinds of two series (Power Platform cards beside the cards of another platform in one diagram, a doc page adding a kind of its own) is a registry written in code today. A mechanism declaring a combination in data, per component type or per block, would make that a configuration. The registry mechanism (`nodeRegistryBuild`) and the kinds as values are the place to start.
- <a id="package-source"></a>**Packages with a version.** A package is named by its folder or by a name found in folders and `node_modules/` ([importing packages](doc_page_impl_package.md#importing-packages)); a package from a registry or a git repository, with a version checked, would need a resolver beside `docPackageDirFind`.
- <a id="package-backend-config"></a>**Packages of a backend started alone.** The service backend learns the packages from the page's sync; its own config (`service-backend.yaml`) names doc pages but no packages, so a backend started without the page does not see their templates.
- <a id="package-dependency-collect-reload"></a>**Reloading a dependency extractor.** The extractors manifests name (`dependencyCollect`) are loaded when the configuration is resolved; a new or changed one needs a restart of the development server ([Components of a doc page](doc_page_impl_mdx_comp.md#components-of-a-doc-page)).

## Command line

- <a id="cli-create"></a>**`npm create`.** `react-doc pack` stages the published package and the installed mode serves from it ([Two modes](doc_page_impl_cli.md#two-modes-a-checkout-an-installed-package)); a thin `create-react-doc` package would let `npm create react-doc@latest my-docs` work as `npm create vite` does, only calling `react-doc init workspace`.

## Card diagram animation

- <a id="animation-visual-edit"></a>**A visual edit mode of an animation.** An animation is edited as its source ([Card Diagram Animation](../package/cloud-dev-vis/doc/card-diagram-usage-animation.md)). Editing the diagram with the framework's editor, and states and tracks from the control area, would be its visual mode; the diagram's part is `DiagramVisualEdit` on `document.diagram`.
- <a id="animation-scrub"></a>**Scrubbing.** The progress on a line shows where a transition is but cannot be dragged; everything is a function of the frame, so a drag would be `seekTo`.

## Connection lines of a card diagram

- <a id="card-record-edit"></a>**Editing the records of a Dataverse card visually.** A `row` or a `column` view of a table only reads, and a Dataverse card's `rows` are written in the source ([Table Card Views](../package/cloud-dev-vis/comp-mdx/power-platform/comp-diagram-er.md#table-card-views)). Its cells could be typed in as a plain view's are.
- <a id="card-view-reader"></a>**Keeping what a reader picked.** The view a reader switches a card to lasts while the card is on the page; a link naming a view, or remembering it per reader, would let a document point at it.
- <a id="route-convert"></a>**Carrying a route to another family of line types.** A route is kept between the right-angled line types and dropped on any other change ([The two layers](../package/cloud-dev-vis/doc/card-diagram-connection-line.md#the-two-layers)). Keeping the anchors, as places, when a right-angled line becomes a curve or back, with handles made up from the directions or the other way round, would save redoing them. `DiagramRoute.js` has what it needs: the anchors' places do not depend on the family.
- <a id="route-auto"></a>**Lines avoiding each other on any diagram.** The ER [arrangers](../package/cloud-dev-vis/doc/card-diagram-arrange.md) keep lines apart and off cards when cards stand in columns, and `connectionOverlapListGet` finds what is left. The layer arrangers do the same for cards in rows, top to bottom. A router that takes free space from the drawn cards wherever they are, with neither columns nor rows, would also serve cards placed in a staircase, and a line between the sides of two cards of one row.
- <a id="route-fixed-anchor"></a>**Anchors an arranger may not touch.** An arranger owns the routes it answers: it removes the anchors of a line and creates new ones ([What an arranger may do](../package/cloud-dev-vis/doc/card-diagram-arrange.md#what-an-arranger-may-do)). An anchor marked as fixed would be kept where it is, with the arranger routing through it, so that an author can apply an arranger again without losing the one bend they care about.
- <a id="arranger-framework"></a>**The ER arrangers for every card diagram.** The lane router and the layer arrangers are in the base series; the ER arrangers still know the ER kinds. The steps to move one up are in [Moving arrangers up to the framework](../package/cloud-dev-vis/doc/card-diagram-arrange.md#moving-arrangers-up-to-the-framework).
- <a id="route-scene-edit"></a>**Shaping a line of a generated scene by hand.** A scene from a provider is read-only, so its lines get their routes from the generator, in code. A way to keep a hand-made route per line of a generated scene, beside the data the scene is made from, would need an identity for the line across runs of the generator (its id is one) and a place to write to.

## Card diagram scenes

- <a id="switch-animation-scene"></a>**What targets look like in a state of an animation over scenes.** A state of [an animation over scenes](../package/cloud-dev-vis/doc/card-diagram-flexible-switch.md#under-the-animation-layer) names a place: a scene and a region. It cannot yet ring a target, hide a node or send a token along a line, as a state of an animation of one diagram does (what the animation layer calls the scene of a state). The targets would be those of the switch scene shown.
- <a id="aws-architecture-description"></a>**An AWS description as an item of a frontend object.** The description of a system, which the scenes of `DiagramAwsArchitecture` are drawn from, is a block of a document, which the scripts of the backends write into ([AWS](../package/cloud-dev-vis/doc/aws.md#scenes-generated-from-a-description)). As an item of a frontend object, several documents could draw one system, each a view of it, and a script would write a file rather than a block of a document.
- <a id="switch-layout-drag"></a>**Moving the nodes of a generated scene.** The reader adjusts the bounding box of a scene; the nodes of a generated scene stand where its generator puts them. Their positions could be kept in the same layout item.
- <a id="migration-report-animate"></a>**The sequences of a run.** The reports of a migration are drawn as tables and cards; the sequence of requests and retries of a batch is not yet a scene.
- <a id="switch-mount-generator"></a>**Mounting a generator, or the items of a frontend object.** A block mounts a document of scenes held in an asset item ([Sources of scenes](../package/cloud-dev-vis/doc/card-diagram-flexible-switch.md#sources-of-scenes)). A generator (`DiagramAwsArchitecture` over a description, the migration explorer over a frontend object) could be mounted the same way: a component exposing the `loadBuild` its block reads its text with as a **scene source** (`expose.sceneSource`), given its text inline or as an asset reference, its registry joined to the viewport's (which waits for [importing kinds between registries](#package-registry-import)). A reference from a mounted source back into the host has no form yet either.
- <a id="switch-mount-edit"></a>**Editing a mounted document where it is mounted.** Its scenes are read-only in the block mounting it. The block session could open them as it opens its own and write the asset item they are held in (a write of the item's head, as a reference block writes it).
- <a id="switch-scene-edit-history"></a>**The canvas history of a scene left.** In the visual mode of a block of scenes, opening another scene commits what the canvas did as one step of the block's history: going back to the scene, its fine-grained undo starts anew. Keeping the editor's store of each scene opened in the session would keep it.
- <a id="switch-edit-at"></a>**A block of scenes entering its visual edit where the reader is.** The session can open on the scene and the camera the reader was at, and give the place back when it ends ([The block session](../package/cloud-dev-vis/doc/card-diagram-flexible-switch.md#the-block-session): `config.edit.at`, `config.at`); an app does it (zatelier-drawboard). A doc page does not yet: its block opens its session on the first scene, fitted. The store of the viewport is the block's (`useCompStateStore`), so the page could read where it is as edit mode starts.
- <a id="switch-scenes-tab-provider"></a>**The tab Scenes for scenes generated from data.** A scene edited in place ([A scene edited in place](../package/cloud-dev-vis/doc/card-diagram-flexible-switch.md#a-scene-edited-in-place)) has no panel of scenes: its provider owns its structure. A provider answering the tree (its `childListGet`) and its commands could fill one, read-only where it says so.

## Card diagram parametric canvas

What the [parametric canvas](../package/cloud-dev-vis/doc/card-diagram-parametric-canvas.md) leaves for later:

- <a id="parametric-tool-bar-edit"></a>**Editing the tool bar.** The tool bar is data (`ParametricToolMap`), and a tool's name, parameters and way of placing are changed on the bar. Adding, removing and duplicating a tool, putting tools under a group, ordering them and keeping one off the bar are written in the config by hand. It waits for [config a layer contributes to](#config-layer-contribute): a tool is an entry each layer may give.
- <a id="parametric-group-inside"></a>**Inside a group.** A reference point inside a card (of a row of it), lines among the copies of a repeat, a repeat inside a repeat. 
- <a id="parametric-locator-line-follow"></a>**A line of a locator that follows something.** A locator is placed as a whole (its origin by its constraint), and each line is a number from that origin. A line whose place is taken from another member (the right edge of a card, a line of another locator) would let a locator measure a drawing instead of only carrying one; sizes dictated by lines would then depend on places, which the solver computes after sizes today.
- <a id="parametric-reference-free"></a>**A reference point picked with the pointer.** A reference point is defined by parameters (an edge and a dividing point, a direction, a corner, lines). Clicking a place of a thing to make one there, snapped to what its outline offers, is left out on purpose for now.
- <a id="parametric-read-switch"></a>**In a block of scenes when read.** The canvas of the switch layer does not draw what the layer draws over a diagram being read (the frames of layouts, a locator shown in full). 
- <a id="parametric-ink"></a>**Handwriting.** Strokes drawn by hand over a scene, with an eraser that takes a whole stroke and one that splits what it touches. `perfect-freehand` (MIT) is the candidate for the outline of a stroke; splitting a stroke is its points cut where the eraser passed.

## Settings panel

- <a id="settings-as-mdx"></a>**The settings panels as MDX documents.** The tabs of the settings panel are built in code from config items (`ConfigPanel`) and custom components (the Workspace graph, the Services tab). Written as MDX documents of a built-in doc page, with components for their parts, they would get everything a document has: blocks that open in the block popup, in-place editing, a layout an author changes without code. The Workspace graph already opens in the block popup through `BlockPopupSurface` with a `popupKey`, the step a block of such a document would take anyway.

## Config

- <a id="config-layer-contribute"></a>**Config a layer contributes to, and config of a feature.** Today a value is **stacked**: a later level replaces the value of the levels below (a `stringMap` alone is merged entry by entry). Some config is of another nature: each layer **provides things**, and what the page has is all of them together. The first place that wants it is the tool bar of the [parametric canvas](../package/cloud-dev-vis/doc/card-diagram-parametric-canvas.md#the-tool-bar): a tool is a template, the package ships some, a doc page or a workspace adds its own, a reader changes or hides one, and none of them should have to repeat the others. Two things to design, both general:
  - **A contributed value**: a key whose value is a collection of items with ids, each level giving items, changing one or taking one away, with an order that needs no renumbering ([ranks](doc_page_impl_config.md#ranks)); the settings panel showing which layer gave each item; a write from the page going to one item of one layer.
  - **Config of a feature**: keys that belong to a feature of a package rather than to one component (the parametric canvas is a feature of every diagram component, and declares `ParametricToolMap` once per component today, as a key of type `any` whose layers do not merge), declared by the feature, written beside `compConfig`, and handed to the components that use the feature.
- <a id="config-declaration-edit"></a>**Adding and removing config keys and declarations from the page.** The doc page layer edits a value a declaration already holds; adding a key to a declaration, removing one, and adding a declaration are written in the files ([The doc page layer](doc_page_impl_config.md#the-doc-page-layers)). The yaml utilities that insert and remove keys in place are the place to start ([YAML utilities](doc_page_impl_yaml_utils.md)).

## Editing


<a id="edit-history"></a>What [the edit history](doc_page_impl_edit_history.md) leaves for later:

- <a id="edit-history-side-panel"></a>**The side panel and the configuration in a history.** Renaming, moving, inserting and removing side-panel items, and the config values written from the page, change yaml files, not documents, and are not in any history ([What is not recorded](doc_page_impl_edit_history.md#what-is-not-recorded)). Their routes already answer what a history needs (`fileChangeList` with the texts before and after, `/side-panel/move`, `/side-panel/node`), and the server's history keeps any file by its path: recording those writes in `DocEditHistory` under the side-panel file, a scope for the side panel (the place of the author in it), and a step that writes through the yaml routes (the configuration loaded again, the page not reloaded) would make them undoable. A file created or deleted with a node is the part to design: the backups of the source layer are the start.
- <a id="edit-history-tree"></a>**Branches of redo.** A new entry drops what was undone in its document ([The order of steps](doc_page_impl_edit_history.md#the-order-of-steps)); Yamd keeps them as a tree and redoes along a branch chosen (`2025/Yamd/doc-mobx/history.md`). The entries of the server could keep their parent and their children instead of a line, with a list of the branches in the menu of the Redo button.
- <a id="edit-history-text-continue"></a>**Undo going on from a text into the document.** Inside a text being typed, Ctrl/⌘ + Z is the browser's own undo, and the document's history is reached once the text is left ([The keys](doc_page_impl_edit_history.md#the-keys)). An author pressing the key again once the text has nothing left to take back expects the document's step, as in an editor where the two are one history. Knowing that the browser's undo of a field had nothing to do (no input event of type `historyUndo` after the key) would let the page leave the block, unchanged, and take the step.
- <a id="edit-history-nested-component"></a>**A component that is not a block asked first.** The undo delivered to a component goes to the block the author is at, by the marker line of the block ([Routing an undo](doc_page_impl_edit_history.md#routing-an-undo)): a component written in a list item, whose block is the list, is not asked, nor one rendered inside another component. Finding the nearest component from the element (a mark of `RegisteredComp` on what it draws, or the subscriptions of the document matched by element) would reach them.
- <a id="edit-history-asset"></a>**Writes of asset items from a document in its history.** The data an asset-backed block saves, and the items of a frontend object a mode writes, are versions of items, not entries of the document ([What is not recorded](doc_page_impl_edit_history.md#what-is-not-recorded)). A step that puts the previous head of an item back (its versions are kept) would let an undo of the page reach them, as an entry of the item beside the entries of the documents showing it.

<a id="edit-structure"></a>What [structural edit](doc_page_impl_edit_structure.md) leaves for later:

- <a id="edit-structure-merge"></a>**Block selection mode merged into edit mode.** One block or list item is selected in edit mode; several blocks selected together, duplicating a block, and the copy / move dialog still live in block selection mode, a mode of its own ([Block selection mode](doc_page_impl_edit_structure.md#block-selection-mode)). Missing in edit mode: a selection of several things (Ctrl / ⌘ + Shift + click adding to it, a range), the entries of the selection's menu in the pinned toolbar (Duplicate, Copy To…, Move To…), and the dialog opened from there; then the mode and its switch can go. `DocEditStructStore.selection` is one thing today, and `DocBlockSelectStore.transfer` takes any list of block indices.
- <a id="edit-structure-multi-item"></a>**Several list items at once.** A structural edit acts on one item, alone or with what is under it. Selecting a run of sibling items and changing their level, moving or deleting them together would be edits of `lib/doc-edit-list.js` taking a list of paths; the tree and the read-back are in place.
- <a id="edit-structure-convert"></a>**Between a block and a list item.** A block cannot be dropped into a list as an item, and an item cannot be dragged out to become a paragraph of its own; a paragraph cannot be turned into a list, nor a list item into a task. Each changes what the thing is, so each needs a rule for what the text becomes (a heading as an item?). The place model of the block operations is already a tree for this ([Choosing where the blocks go](doc_page_impl_block_ops.md#choosing-where-the-blocks-go)).
- <a id="edit-structure-split-lines"></a>**Enter in an item of several lines.** Enter splits an item whose text is one line, and a text block at any place of its lines. In an item whose source has several lines otherwise (two paragraphs, a component with its data) Enter is a line break, since a place in such a source is not always a place the item can be cut at (inside a fence, inside a tag). Splitting between two paragraphs of an item could be offered.
- <a id="edit-structure-write-wait"></a>**The moment an edit of the editor takes.** Enter, Backspace and Tab in an item write the list and read the document again before the next item opens: about 60 ms on a short document, 100 to 200 ms on a document of 70 blocks. The keys typed in that moment are kept and typed into the item that opens, so nothing is lost, but the caret is not seen for that moment. Opening the next item at once over the text just written (as `blockTextPending` shows a saved block) and compiling behind it would take the pause away.
- <a id="edit-structure-atom-more"></a>**More things as chips of the text of an item.** The editor of a list item types its code blocks as one character each, icons in the line and blocks of other views on a line of their own ([Code blocks in the text of an item](doc_page_impl_edit_structure.md#code-blocks-in-the-text-of-an-item)); a formula of LaTeX is an atom of a kind, a thing a component writes inside a text ([Atoms of a kind](doc_page_impl_edit_structure.md#atoms-of-a-kind)); every other block of the item (an image, a component with its data) is still typed as its source. Any block could be a chip the same way: a kind of atom for it, its chip drawing a copy of the rendered block as a code block's does, its editor a dialog or the block's own editor below it. Also open: the view of a code block standing among text is chosen in its text (`view=`), not from the page (the list menu of an item offers the views for an item that is one block only; the dialog of the lines could offer them); ← and → step over the chip of a block among the text of an item rather than going into its lines (↑ and ↓ do go into them).
- <a id="edit-structure-quote"></a>**Lists that are not blocks.** Only a root-level list has an item model: a list inside a quote, or the items of a list a component renders from its own data, are edited with what holds them.
- <a id="edit-body-redraw"></a>**What a write still costs.** A write draws only what it changed ([A write draws only what changed](doc_page_impl_edit.md#a-write-draws-only-what-changed)), but it compiles the whole edit body again (`docEditCompile`, some 20 ms on the example structure page in a development build), half of it the parse of the whole document: a compile of the changed blocks only would need a parse by block that keeps what spans blocks (definitions, footnotes, the ids of headings), or the compile in a worker, which the plugins calling the stores of the page (structured data, languages, the onBlockList of the edit layer) do not allow as they are.
- <a id="edit-math"></a>**LaTeX math, after its first version** ([the component math](../built-in/comp-mdx/math/comp_math.md)). A formula is typed as a chip in a paragraph and the text of a list item, and a block of math in place; a formula in a heading, a quote or a cell of a table is still typed as its source (the kind is asked only by the editors of a paragraph and an item). The field of a formula floats over the lines below it, so they are hidden while it is open; near the bottom of the window it could open above the formula. The macros and options of KaTeX are its defaults: a document or a doc page cannot declare its own (`\R` for `\mathbb{R}`), which the compile (`rehype-katex`) and the component (`mathRender`) would both read from the config.
- <a id="edit-mdx-embed"></a>**The MDX block, after its first version** ([MDX blocks](doc_page_impl_mdx_embed.md)). A block added from the insert menu of a block opens in the source mode of a component, its fence in view; opening its popup with the empty document in edit mode would be the way it is added by `/mdx`. A block in the document of another block (an MDX block in an MDX block) has a path that names it (the path splits at its last separator, `embedPathParse`), but it is untried, and the page has one popup for them: the inner one opens in the place of the outer one, with no way back but opening the outer one again. A title with a comma loses it (a marker separates its props by commas): props of a marker in quotes would keep it. The path of an embedded document names its block by its line, so an edit above the block while its popup is open makes the open document a moved one, read again from the block; a block id kept across edits would name it for good ([Places in a document](doc_page_impl_nav.md#places-in-a-document)).

<a id="edit-cell"></a>What the [cell editing kit](doc_page_impl_edit_cell.md) leaves for later:

- <a id="edit-cell-kind-declare"></a>**Token kinds of a doc page or a package.** The registry of kinds holds the package's and the host's ([Token kinds](doc_page_impl_edit_cell.md#token-kinds)); a component brings its own with each cell (`useCell({ tokenList })`). A kind that every cell of a doc page should accept (a ticket number, a term of a glossary) has no place to be declared: a `cellTokenList` of `comp.yaml`, mounted like the components, would be one more layer of `cellTokenByIdBuild`.
- <a id="edit-cell-object-search"></a>**Finding an object by words in `/object`.** The walk starts at the types, and words narrow one step at a time ([The walk of `/object`](doc_page_impl_edit_cell.md#finding-something-to-write-the-walk-of-object)): typing `dune` finds no book until its list is reached. A step listing objects by words across types needs the moderated search ([Search](doc_page_impl_obj_search.md)) read at once from a session, and a book is not an object but something inside one, so the providers completing inside their objects would also have to search inside them.
- <a id="edit-cell-row"></a>**Several fields opened together.** `CellField` opens one field of the page at a time ([The field](doc_page_impl_edit_cell.md#the-field)). A row whose cells open together, Tab going through them, is built by its component from `CellEdit` today, as the rows of a history of the Japanese-style CV are; a field group of the store (the fields of one row, one focused, saved together) would make it one more ready piece.
- <a id="edit-cell-page-text"></a>**Tokens in a text cut between its lines.** A paginated piece draws its cells with `CellValue`, so a page shows a link or an image as the block does ([What the kit does not do](doc_page_impl_edit_cell.md#what-the-kit-does-not-do)). A piece cut between the lines of its text (a section of text of a CV) is measured and cut in its plain text, and is drawn from it: a token there prints as its text. Cutting a text that holds drawn tokens needs the cut expressed in the cell text rather than in the characters drawn.
- <a id="edit-cell-style-canvas"></a>**Styles of words on a canvas.** A cell says whether its words take styles ([Style kinds](doc_page_impl_edit_cell.md#style-kinds)); the labels typed on a canvas (the color block and the shapes of the card diagram of cloud-dev-vis) say no for now, and are typed as before. Switching them on needs the bar and the styled surface checked on a zoomed canvas, in the page and in the drawboard built on the framework.
- <a id="edit-cell-style-compose"></a>**A text composed at the side of another style.** What is typed takes the style of the caret's side after the browser typed it ([Typing styled text](doc_page_impl_edit_cell.md#typing-styled-text)), so a text composed by an input method where two styles meet, or with a style chosen for what comes next, is shown in the style the browser typed it in until the composition ends. Composing it in its style from the start needs a place of that style made at the caret before the composition begins.
- <a id="edit-cell-style-token"></a>**A token in a style.** A token has no style: a link or a value of a profile named in bold words is drawn as its kind draws it. A style of a token would be a parameter of the token (`{{body|b}}`), which its kind's drawing would have to honor.
- <a id="edit-cell-backend"></a>**Inside the objects of a service.** `innerComplete` is a capability of the providers of the page ([Inside an object](doc_page_impl_obj.md#inside-an-object)); the backend peer forwards none, so `/object` writes a todo of a service but cannot walk into a list of them. An object api `innerComplete` of the scripts, answered through the peer and kept by the registry for a few seconds, is the shape.

## Source

- <a id="source-file-rename"></a>**Moves beyond one file.** A file is moved or renamed from the page with every reference to it (links of every document, the side panels and entries naming it), into and out of virtual roots ([Relocation](doc_page_impl_nav_backlink.md#relocation)). Missing: a **folder** moved or renamed (every file under it in one plan; `relocatePlanBuild` takes a list of moves already, a folder would be its files, and a folder of a virtual root only its records), and a file of a mirrored folder moved by dragging its item; **the undo of a move** as one step (the move back with the references put back, recorded beside the edit history, which today only lets the moved document's entries follow it, `DocEditHistory.pathMove`); and the references relocation does not rewrite yet: the source dependencies of asset versions (`dependencySet` of the store, refused on a locked version), the document of a playground (`playground.yaml`), the `sourceFolder` of a side panel when a folder moves.

- <a id="doc-managed-cloud"></a>**Managed documents on a cloud.** A virtual root is kept on the local disk in two forms, plain and pack ([Managed documents](doc_page_impl_doc_managed.md#toward-a-cloud)); a page hosted on a cloud would keep its roots as pack objects in an object storage (s3: `{rootId}/{docId}.rdoc`, listed by reading each record at the head of its object). Missing: a driver of a remote root behind the one door of the source (`plugin/doc-source-access.ts`) and in the page (reading a bucket without a development server: the decoding is `lib/doc-managed-pack.js` already, with `CompressionStream`), writes checked by version (`If-Match`, the edit layer's `hashBase`), the authorization of the auth layer ([Auth](doc_page_impl_auth.md)), and moving a whole root between the local disk and a bucket, as a partition of a frontend object moves between storage points ([asset storage](doc_page_impl_asset_storage.md#changing-the-storage-of-a-partition)).
- <a id="doc-managed-block-ref"></a>**What the ids of blocks are for.** A document of mode block keeps an id per block and list item, kept through edits ([The block mode](doc_page_impl_doc_managed.md#the-block-mode)). Nothing uses them yet: a reference to a block by its id (`~notes/a.md#^k3f9a2`, resolved by the navigation layer like an anchor, kept valid by the ids instead of a written `Anchor`), a backlink to a block, and a remote root writing one block instead of a document.
- <a id="doc-managed-root-change"></a>**A virtual root renamed, deleted, or moved between doc pages from the page.** A root is made and its name, mode and form changed in the Managed documents tab; its alias is the root of every path of its documents, so renaming it is a relocation of all of them, and deleting it a deletion of all of them with their references; both, and moving a root folder to another doc page, are done on disk today.

## Navigation

- <a id="nav-reading-place-reload"></a>**Reading places across a reload.** Going back to a document, or opening again one read before, brings back where the reader was, by the structure of the document ([Reading places](doc_page_impl_nav.md#reading-places)). The places are kept in memory, on the history entries of `DocStore` and per document, so a reload of the page, or a page opened again later, starts without them, though the browser's history still has its entries in query mode. Keeping them would mean writing the place of an entry into `window.history.state` as it is left (a `replaceState` before the `pushState` of a navigation; on a move in the history the browser has moved already, so the page would record the place while reading, not only when leaving), and the latest place per document into `sessionStorage`; a place is small plain data already.

- <a id="side-panel-home-item-path-rewritten"></a>**A home item path kept true through edits of the side panel.** `homeItem` names the item the page opens at `/` by its path of labels or ids ([The home of the page](doc_page_impl_side_panel.md#the-home-of-the-page)); renaming a label in place, moving the item or removing it leaves the path naming nothing, and the page then opens `homeDoc` or the first item, with a warning in the console only. Missing: the writes of the side panel (`doc-side-panel-text.ts`, `doc-side-panel-move.ts`, `doc-side-panel-node.ts`) rewriting a `homeItem` of the workspace file or of the entry whose path goes through what they change, as relocation rewrites a `homeDoc` naming a moved document (`doc-relocate.ts`), and a path naming nothing shown where the author sees it (the Workspace tab), not only in the console. To start from: `sidePanelItemPathResolve` (`lib/side-panel-item-path.js`) tells which node a path names, and the in-place yaml edit (`doc-yaml-edit.ts`) writes one value.

## Search

- <a id="unified-search"></a>**A unified search of the page, replacing the search of fumadocs.** The page searches in several places, each for one kind of thing: the dialog shipped with fumadocs finds the text of documents (headings and paragraphs, [Search](doc_page_impl.md#search)), the field of the side panel finds items by their names ([Searching the items](doc_page_impl_side_panel.md#searching-the-items)), the object search finds the objects of the registry ([Object search](doc_page_impl_obj_search.md)), and the command palette finds apis. A reader should not need to know which search holds what. One search implemented by the page, in the field of the side panel and in a dialog on ⌘K, with its results grouped by kind (items, documents and their sections, objects, apis), would replace the dialog of fumadocs, which then goes from the page: its buttons are hidden already (`searchToggle: { enabled: false }` of `DocsLayout`, and a css rule for the panel of a collapsed sidebar), and only its key still opens it. To start from: the matcher of the dialog over structured data (`DocStore.searchQuery`), `sidePanelSearchMatch` (`lib/side-panel-search.js`), and the moderated object search, whose providers answering by kind are the shape the other kinds would take.
- <a id="side-panel-search-source-folder"></a>**Searching inside a source folder.** The search of the side panel stops at the item of a source folder: it finds that item by its name, and not the files and folders generated below it ([Searching the items](doc_page_impl_side_panel.md#searching-the-items)), so a file deep in a mirrored folder is found only by unfolding the folder. The generated items are in the tree model already, with their routes (`itemOutlineById`, marked `generatedFrom`): including them in `sidePanelSearchEntryListBuild` as results of their own, after the authored items and bounded (a folder can hold many files), would do it, as would the unified search above finding the files of the source.

## MDX components

- <a id="pagination-layout"></a>**Layout beyond a column of pieces.** Pagination places the pieces of a flow one after another down a page and cuts them where their types say ([Pagination](doc_page_impl_pagination.md)). On the same flow, measures and plan, a richer layout: floating elements placed beside or around the flow (a figure, a sidebar), elements fixed to every page (a header, a footer, the page number drawn on the sheet), keeping a piece with the next one (a heading with its paragraph), several columns, a page of another size inside the flow; and a block of a document that is a pagination environment for the blocks inside it, so that any component declaring the contract is paginated in a document, not only by the component that draws the environment itself (the CV's view Pages). Each is a new kind of thing the planner places, decided by the same measures, so a component's pieces stay as they are.

## Events and component state

- <a id="event-subscription"></a>**Subscriptions by other subjects than a block.** The event layer delivers events to components at a place of a document (`subscribe` / `publish` of the router, keyed by document and block line; `placeReveal` of the backlinks, [Events delivered to components](doc_page_impl_event.md#events-delivered-to-components)). Missing: a subject that is not a block, so that a component is told when its asset item changes instead of asking (`assetRefreshRequest`, [Changes made by others](doc_page_impl_mdx_comp.md#changes-made-by-others): the asset service layer would publish on `doc-asset-change` with the object as subject), and the service events below with an instance as subject; one more key of the subscription and of the matching in `publish`.
- <a id="state-two-tabs"></a>**Component state across browser tabs.** Two browser tabs of one page keep separate state objects; keeping those of one key in step needs a channel (`BroadcastChannel`, a websocket), the one subscriptions would use; the key format is already the address ([Extending the layer](doc_page_impl_mdx_comp_state.md#extending-the-layer)).

## Asset service layer

- <a id="asset-storage-notify-local"></a>**The local types telling which tab wrote.** A remote point tells the page of a change with its actor, and the page does not read again what it wrote itself ([Being told of changes](doc_page_impl_asset_storage.md#being-told-of-changes)). The development server reports a file changed on disk to every tab (`doc-asset-change`) without saying which tab wrote it, so a tab reads again what it just wrote. Missing: the asset api of the development server reading the header of the [client instance](doc_page_impl_client_instance.md), and its change events carrying the actor.
- <a id="asset-storage-notify-topic"></a>**Finer topics of a remote point.** The channel of `aws-utils.remote` hears a whole space (`space/{key}`), and the page leaves out the partitions it does not hold. A space shared between accounts, or one holding many partitions of other pages, would want a topic per partition, and per account the topics it may hear.
- <a id="asset-storage-item-move"></a>**One item moved between a remote point and another point.** A whole partition moves between any two points through the page ([Changing the storage of a partition](doc_page_impl_asset_storage.md#changing-the-storage-of-a-partition)); `asset/move`, `asset/attach` and releasing an asset (`asset/remove` with `isAssetKept`) are refused when one side is a remote point. Missing: the same read-then-write for one item, and the removal of the item at its source for good (the development server only marks an item deleted, which would leave its id in two places).
- <a id="asset-storage-remote-test-result"></a>**A test result recorded into an item of a remote point.** `test-case/result/set` is a route of the development server and writes an item it holds; an item of a remote partition is refused. The page would build the new text itself and write it as an update.
- <a id="asset-storage-backup"></a>**Backups of partitions.** The api set `backup` is a contract: a point keeping copies of whole partitions, its own or those of another point, each identified like a partition plus a time, listed and brought back from the Asset service tab.
- <a id="asset-storage-point-edit"></a>**Declaring storage points from the page.** The points are written by hand in `asset-storage.yaml` of the workspace or of a doc page; the Asset service tab lists them and the problems of the files, and does not add, change or remove one.
- <a id="asset-storage-standalone"></a>**Items outside a partition at another point.** Only a partition of a frontend object is bound to a point other than file-tree; the asset folders of a doc page and the assets of an object without a folder of its own are always file-tree (`isStandaloneItemHeld`).

## Auth

<a id="auth"></a>What the [auth service layer](doc_page_impl_auth.md) leaves for later:

- <a id="auth-consumer-policy"></a>**Which consumer may use which session.** Every part of the page may ask every session for a credential ([Credentials for consumers](doc_page_impl_auth.md#credentials-for-consumers)). A consumer already says who it is (`{ kind, id, label }`) and the layer records who asked. Missing: a policy, declared with the provider (which storage points, which components) or decided by the person at the first use ("let the storage point Cloud use this session?"), checked in `credentialGet`; and a credential narrowed to what the consumer needs (an audience, a scope) where the identity provider can issue one.
- <a id="auth-redirect-kind"></a>**Kinds that sign in through another window.** The dialog of a kind is a form inside the page, which suits a provider with an api of its own (Cognito). A provider that only signs in on its own page (Google, a hosted login) needs a popup window or a redirect with a callback address registered per origin: a second shape of `SignInComp`, and the session picked up when the window comes back.
- <a id="auth-identity-link"></a>**One person, several providers.** A session is of one provider. A person signed in to two providers that are the same user to a backend (two identities linked to one user id) is two sessions to the page; `identity.userId` is where they would meet.
- <a id="auth-session-tab"></a>**Sessions in step across tabs.** A session kept in `localStorage` is read when a tab first asks; signing out in one tab is seen by another at its next refresh of a credential. The channel of [component state across tabs](#state-two-tabs) would tell them at once.

## Api registry

In the order they would matter ([Unified api registry](doc_page_impl_api.md)):

- <a id="api-registry"></a><a id="api-hotkey-client-map"></a>**Keys edited from the page.** The keyboard maps are files of the package, the doc pages and the workspace, and the host's; the reader can only pick a map of a doc page ([Where the maps are](doc_page_impl_api_hotkey.md#where-the-maps-are)). A client map kept in the browser above the stack, edited in the API tab (a key, an api chosen from the registry), would be the counterpart of the client config layer; `DocHotkeyStore.mapListStack` takes one more map.
- <a id="api-job"></a>**An api that is a job.** An api answers within the call ([Core concepts](doc_page_impl_api.md#core-concepts)); a long operation (a build, a scan of every document) has no form yet. The jobs of the service backend (`serviceJobGetRequest`, polled) are the model: an api returning a job id, and `api/jobGet` to follow it.
- <a id="api-remote-build"></a>**Remote calls without the development server.** A built page keeps its apis for the page's own ui only: the bridge is a route of the development server ([Remote callers](doc_page_impl_api.md#remote-callers)). A page served otherwise would need the same bridge in its server, with the authorization a page on the network needs (the question of [a deployed backend](#service-deployed-backend)).

## Object registry

<a id="object-registry"></a>In the order they would matter ([Objects and Types](doc_page_impl_obj.md)):

- <a id="object-registration-persistent"></a>**Persistent registrations and pins.** A registration lives in the memory of its registry (`registrationByRef` of the page, `registration_by_ref` of the backend) and is gone with a restart; a reference that someone holds for good (a group of a service naming a document, a timeline naming an asset) cannot ask the registry to keep tracking its identity and provider across restarts, nor be told it became `missing`. A pinned registration kept beside the backend config (as `service-kernel.yaml` keeps the routes), and the page registering the references its documents hold, are the place to start; the statuses already say registered from found.
- <a id="object-type-version"></a>**Versions and contracts of types.** A type has an id and no version: two templates extending `core.task` agree by declaration, and a change of what a type promises reaches every provider at once. A version in the id (`core.task@1`), assignability across compatible versions, and a check that a provider's answers keep the promise (the summary keys, the update it accepts) would make a type a contract; the [contract behind an infra name](#service-reference) is the same question for services.
- <a id="object-type-source"></a>**Declared types on the backend.** The kernel's registry knows the built-in types and the templates'; a type declared in yaml ([Declaring a type](doc_page_impl_type.md#declaring-a-type)) is known to the page only, so a service answering with `example.ticket` has a child of the roots on the backend, and a backend-side filter by its parent misses it. The page already tells the backend of the doc pages it loads (the sync of `doc-service-server.ts`); the declared types would go with it.
- <a id="object-relation-diagram"></a>**A diagram of relations.** A card diagram draws objects as nodes, but its lines are its own data; a diagram whose nodes and lines come from a relation query (the dependencies of the instances, the links of a part, the members of a group), laid out automatically, would show the registry's graph. The relation queries and `ObjectView` nodes are what it would be built from.
- <a id="object-backend-page"></a>**The backend asking the page.** A service finds the page's documents only as the page registered them (`registered`, possibly stale); it cannot resolve a section, read a document or follow a link. A route from the backend to the page's providers while a page is connected (the remote api channel of the development server, [Remote callers](doc_page_impl_api.md#remote-callers), is the model) would make the page a provider of the backend's registry.
- <a id="object-resolve-batch"></a>**Batched resolves and pushed changes.** Each object drawn resolves alone (a query primes its objects, so a list costs one request), and the page learns of a change of a backend object only by asking again after the provider's cacheSecond or a version change. Resolving the references of one render in one request, and the backend pushing `object_changed` to the page (the [subscriptions](#event-subscription) of the event layer), would cut both.
- <a id="object-search-line"></a>**Objects as the ends of a line.** The create panel of a card diagram adds an object as a node ([In a card diagram](doc_page_impl_obj_search.md#in-a-card-diagram)); the panel of a line does not search objects for its ends, nor does a line drawn from a relation of the registry exist. The search session the create panel uses is the part to reuse.
- <a id="object-search-index"></a>**An index for the search.** A search plans by the hosts, counts, and fetches a bounded page of each provider; a provider with many objects and no word it can filter by is counted, never searched inside. A provider-side search index (a full-text table of an instance, the page's search index of documents, `DocSourceStore.searchDocs`, for the headings) answering the words themselves would let a search find inside it; `count` and the pushed word are the protocol it would extend.
- <a id="object-backend-write"></a>**Creating and deleting the objects of a service.** The registry hands `create`, `delete`, `relationCreate` and `relationDelete` to the provider that owns what they change ([Writing through the registry](doc_page_impl_obj.md#writing-through-the-registry)), and the page's providers implement them (the frontend objects, the asset store); the backend's registry has `update` only, so a todo cannot be added through `object/create`, only through the instance's own apis. Object apis `itemCreate`, `itemDelete`, `relationCreate`, `relationDelete` of a script (`@object_api`, with `createTypeList` in `objectProvide`), the kernel's routes for them, and the peer provider passing them on are what is missing; the page's side is in place.
- <a id="object-update-authorization"></a>**Who may change an object.** An update goes through when the consumer allows it and the provider offers it; the user behind the change is not known to the provider ([Authorization](doc_page_impl_service_kernel.md#authorization)), and the page's providers offer no update at all (a section, a group written in a document are changed by editing the document). Updates of document objects through the edit layer, and the end user carried to a service provider, are both missing.

## Frontend objects

<a id="object-frontend"></a>What the [frontend object service layer](doc_page_impl_obj_frontend.md) leaves for later:

- <a id="object-frontend-store"></a>**Components in the folder of an object.** A partition of an object can be held by a storage point of its own choosing, a backend among them ([Where a partition is stored](doc_page_impl_obj_frontend.md#where-a-partition-is-stored)). The components a type's modes name stay outside the folder: an object moved to a doc page without them draws an error line; a `comp-mdx/` inside the object folder, mounted with the doc page's, would carry them too.
- <a id="object-frontend-schema"></a>**Kinds beyond their declaration.** A kind is a type of the registry with a content and, for data, a schema checked on the way in and reported on the way out ([Kinds of data items](doc_page_impl_type.md#kinds-of-data-items)). Left for later: a schema naming the schema of another kind (`$ref` to a kind, so a kind reusing another's shape need not restate it); a kind whose schema changes while items were written under the former one (a version of the kind, and a migration of its items, are the [versions of types](#object-type-version) again); acceptance that cannot be declared because it depends on the other assets (a note naming a book that exists), which needs code of the type the development server cannot run as things are, a check the page asks of the component of the type before the write being the likely shape; kinds the page itself offers every type (an image, a PDF, a Markdown document) so that a type need not declare them; an asset of an object typed as its kind in the registry (its descriptor below `frontend.item`, not only `asset.item`), so that a view can be chosen per kind; and the declared kinds known to the backend's registry ([TODO](#object-type-source)).
- <a id="object-frontend-slot"></a>**Slots: objects that need other objects.** A frontend object reaches another today by a reference written in its data and read with `otherGet` (a CV naming its profile), and nothing above the mode knows the two belong together. Objects will need more: one object **containing** or **managing** another (created, copied and deleted with it, perhaps lying inside its folder), and one object **connecting** to others to work (a profile to read, a store of files, an object providing a service: an account, a model, a backend), each connection with a label saying what it is for. A type would declare these as **slots**: `slotList: [{ id: profile, label, typeList: [cv.profile], count: one | many, isRequired, relation: uses | contains }]`; an object fills a slot with references (in its entry, so it travels with the object), the page resolves them and checks their types, reports a slot required and empty or filled with an object of another type, and a mode reaches what fills one by the slot's name (`service.slotGet('profile')`) instead of a reference of its own. In the object registry a filled slot is a relation (`core.contains`, `core.reference` with the slot as its key), so a diagram of objects and the Frontend objects tab show what an object depends on. The profile of a CV is the first slot; objects providing services ([Services](doc_page_impl_obj.md#services)) are what most slots would be filled with.
- <a id="object-frontend-version"></a>**An asset pinned to a version.** A frontend object reads the head of each of its assets: a record of its item lists says `{ key, kind, itemId, name, pathList }`, no version ([Naming and finding the assets](doc_page_impl_obj_frontend.md#naming-and-finding-the-assets)). An object whose part must stay as it was while its asset is revised (a quotation of a document at a version, a released configuration) would list `versionId` beside the object id; the asset store already resolves a reference to a version (`refQuery` with `versionId`), and the mode api, the index and the writes of the entry are where it would be carried.
- <a id="object-frontend-remote-object"></a>**An object declared by a storage point.** A partition can live at a remote point; the object itself (its folder, its entry asset) is in the folders of a doc page, so a built page shows only the objects it was built with, and a person cannot make a new object from a built page. An object whose declaration and entry are held by a point (listed by `partitionList`-like `objectList` of the point, per account) would make a built page a place where objects are created. The entry asset would then be an item of a partition, and the layer's "the folder says the object exists" would gain a second source.
- <a id="object-frontend-change"></a>**Being told of a change.** A mode re-renders when the asset store hears of a change (the page's own write, a file changed on disk); a mode holding something derived (an engine, a draft) is not told which asset changed. The [subscriptions by other subjects than a block](#event-subscription), with the object as subject, are the channel it would use.
- <a id="object-frontend-partition-build"></a>**A build without the partitions kept out of git.** A playground document is left out of a static build, but a partition of a frontend object that git ignores (`item/real/`) is built like the rest when the checkout has it ([Partitions of a frontend object](doc_page_impl_dir.md#partitions-of-a-frontend-object)), so publishing from a checkout holding private data means moving the partition away first. The partitions a type declares with `isGitIgnored` would let `react-doc build` leave them out the way `playgroundLeaveOut` does.

## Portal

What [portals](doc_page_impl_portal.md) leave for later:

- <a id="portal-settings"></a>**A Portals table in the settings panel**: every portal with its provider, its component and what does not fit, where the Frontend objects tab lists the types. Today `portal/list` answers it, and a portal that cannot be drawn says so where it is opened.
- <a id="portal-object"></a>**A portal as an object of the registry, and a link to one**: found by a search, listed by `ObjectList`, written in a document as a link the navigation layer follows (`[Library](portal:frontend:…/library#/book/…)`) or a token of a cell. Today a portal is opened by its address, the switcher and the apis; a Markdown link holding `?portal=…` is not followed as one.
- <a id="portal-launch"></a>**A launch page**: the portals of a workspace as tiles (`PortalIcon` at a large size), for a deployment with many apps. The switcher is the only list today.
- <a id="portal-provider"></a>**Other providers**: a service instance, a document. The registry takes any provider (`register`), but only frontend objects declare portals in yaml.
- <a id="portal-param"></a>**The place of a portal typed**: `at` is one string of the app's own; a declared shape (parameters with types, as an api has) would let the palette ask for them.

## Service layer

In the order they would matter ([Service layer](doc_page_impl_service.md)):

- <a id="service-reference"></a>**A rigorous reference to a service.** A service is referred to by a name string today ([Naming a service](doc_page_impl_service.md#naming-a-service)); its objects already have references and types of the [object registry](doc_page_impl_obj.md), which a contract of an infra name could be declared with. Missing: a **contract** behind an infra name (its apis and their versions, the storage type it promises), declared by the templates implementing it and checked when a dependency is resolved, so a consumer can require `sqlite@1` and the kernel can refuse a provider that does not implement it; and an **identity** of a template beyond its id and name: a content hash of its files at a version (computed when a version is recorded, so the backend also notices files changed without a new version) and a signature of its author, so an instance can prove what it was created from and a template from elsewhere can be trusted or refused.
- <a id="service-backup"></a>**Backup to another storage, and migration of a consumer's data.** A backup on the local disk exists: the `local-backup` infra service keeps a consumer's data as zip files in a folder ([The local-backup infra service](doc_page_impl_service_storage.md#the-local-backup-infra-service)). Missing: the `backup` storage operation to **another storage** (a cloud object store the backup infra would depend on, the zip files of local-backup being what is sent), with the backup status reported as part of the storage (last backup, verified, pending changes), since reliability is a state to observe, not a flag; a backup **scheduled** by the infra itself (a resident `run()`) instead of asked for by the consumer; and moving a consumer's database from one sqlite instance to another when a name is rerouted (a backup checked out into the other instance is the manual way today).
- <a id="service-data-clear"></a>**What a deleted instance's data becomes.** Deleting an instance keeps its folder (`.deleted-…`) and everything it had in infra services: its database in sqlite, its backups in local-backup, which lists them as orphans to delete by hand ([Lifecycle and hooks](doc_page_impl_service_kernel.md#lifecycle-and-hooks)). Missing: a policy, declared per infra service or chosen at the deletion (keep, remove, remove after a time), carried by the `onDestroy` hook or by the kernel asking every infra the instance depended on, so that nothing is removed by surprise and nothing is forgotten either; the orphan listing of local-backup and sqlite's `consumerList` are what such a policy would act on.
- <a id="service-log-audit"></a>**The audit and the backup of the logs.** An audit group (permissions changed, instances deleted, routes set) with a stricter retention than the operational records, and the backup of the log database through a storage infra once there is one to back up to ([The logging infra service](doc_page_impl_service_kernel.md#the-logging-infra-service)).
- <a id="service-permission"></a>**A policy of permissions.** Which caller may call what, which infra names an instance may add at runtime and with which scope, in one place, with the end user behind a page request carried through the calls and into the log's principal ([Authorization](doc_page_impl_service_kernel.md#authorization), [Dependencies](doc_page_impl_service_kernel.md#dependencies)).
- <a id="service-template-update"></a>**Comparing and updating from a template.** With the hash above, the Services tab could say which files of an instance differ from its template's version and from the template's current version; `Update from template` (copying chosen files again, the data kept) and `Recreate` would be explicit steps, never a template change reaching instances by itself; where a newer script needs another shape of data, the update carries a migration of the instance's state.
- <a id="service-template-from-instance"></a>**Templates from instances.** Saving an instance (its script and dashboards, not its data) as a new template, a fork with its own id and versions.
- <a id="service-deployed-backend"></a>**A deployed backend.** The backend on a server, reached by a built site or a development server alike by its address alone ([Reaching the backend](doc_page_impl_service_dashboard.md#reaching-the-backend)). It needs to be reachable from the page's origin (a reverse proxy on the site's origin, or CORS for the origins its config names; it sends no CORS headers on purpose today), its doc pages listed in its own config instead of the development server's sync, and the permissions above, since a page on the network is no longer the only caller. Its address would then come from `config.yaml` for a build too, not only from a host passing it.
- <a id="service-call-any-component"></a>**Calls from any component.** Only dashboards send `serviceApiCallRequest`; a component of the registry that is not a dashboard could call an instance by a target too, as the page does.
- <a id="service-isolation"></a>**Execution isolation.** Instances share one process; a template could declare how its instances run (the shared process, a worker, a process of their own, outside the backend), for scripts that are not trusted or need resources of their own; a hook that does not return could then be killed instead of recorded.
- <a id="service-event"></a>**Service events.** The lifecycle changes, the dependency changes and the log records share one envelope only in the log; a subscription (a dashboard told that its instance restarted, a service told that its dependency came back) would be the next channel beside the calls, on the [subscriptions](#event-subscription) of the event layer.

## Source: object roots

<a id="source-object-conflict"></a>

- **An internal representation of name and id conflicts of object roots.** A path `~${frontend.name:x}/…` (or `~${frontend:x}/…`) that several objects answer to resolves to the first, and the only trace is a `warning` on the resolution, logged once in the console (`DocSourceStore.resolveWarningSet`). Keep the conflicts as state instead: when the providers register their roots (`docProvidedSet`), work out per namespace which names several objects have and which id of one object is the name of another, hold it in the source store (`rootObjectConflictList: [{ namespace, ref, by, rootList }]`), and let the places that can act on it read it: the Frontend objects tab (a problem on each object involved, with the others), a link written by such a name (the candidate list a file name with several matches already gets, or a mark beside the link), and the build (a warning naming the documents that use the ambiguous spelling, from the link index). The resolver then asks this representation rather than scanning the roots per link.
