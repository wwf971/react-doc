# Agent guide

Development guidance for this project is in `main/ai-dev.md`; read it first. This file lists the service layers that already exist, so that before building a feature an agent can judge whether it is missing or already there, and in the latter case find it.

## When about to do something, read this first

Each row names a kind of change and the document that states what the result must satisfy. Read the document before starting; the points in bold are the ones most often missed.

| When about to ... | Refer to |

## The TODO list

What the design leaves for later is listed in one place, `main/doc_page_impl_TODO.md`, grouped by functional area; the design documents only point to it. Keep it that way:

- **Before building**, check the list. When the request matches an item there, say which item, and ask the user to confirm that it is what they mean before starting.
- **After building**, compare the result with the item: remove an item the work fully implements (its design now belongs in the design document, as what exists), and rewrite an item it implements in part so that it says what is still missing.
- A new gap found while working goes into the list under its group, never as a TODO paragraph in a design document.

## Existing service layers

Some features already implemented which you can utilize in case you need. Check this list before building something, so a capability that already exists is extended rather than built again.

<!-- Principle when editing this list: each entry briefly states what the service layer provides, and points to its core markdown document (doc_page_impl_xxx.md). Do not mention folder / file locations here; the core document lists its implementation files. -->

- **Environment**: Answers where the page runs (vite development server, static build; more kinds can be added) and what that allows: editing, creating files, the asset api, the service backend. Every check of "can this be done here" goes through it (`isCapable`, `reasonGet`), also for components (`config.env`). Refer to `main/doc_page_impl.md#the-environment`.

- **Doc page source service layer**: Maintains an internal representation of the workspace (the root-level doc pages of one deployment, each doc page one thing however often it is included, named by an alias unique in the workspace), of the roots of every doc page (named by aliases, so a folder can be renamed and same-name folders coexist) and of the files and folders below them, each file named by its full source path `~page:root/path`. Resolves every spelling of a reference, the local doc page first. Provides file creation and deletion from the page (a deleted file goes to a hidden backup, in the same request as the write that makes it unused), the documents that link to a file, a refresh of the source for changes the file watcher missed, a location prompt any caller can open with its own folders, auto-complete dropdown ui component and logic for user to find / specify a file / dir of the source, the same for a path of the os file system (listed live by the development server), `.gitignore`-like `exclude` patterns on source rules, and the Workspace tab of the settings panel (editing the workspace file in place, temporary doc pages mounted on the development server, a React Flow graph of the doc pages, their includes and alias conflicts). Refer to `main/doc_page_impl_source.md`.

- **Doc page side panel service layer**: Maintains an internal representation of the side panel tree declared in yaml, kept up to date when the yaml changes, from which document order, routes, parts and sub documents are derived. A side panel is a resource with an id and can include another side panel. Provides the tree ui, an item label component that can be replaced per item, localized labels, and in edit mode, with write-back into yaml: renaming, moving, inserting new folders and new (empty) documents, binding an item to another document or source folder or detaching it, removing an item (with its document, after showing who links to it), and reading an item's files again (refresh), through a context menu. An item mirroring a source folder shows a file tree whose items follow the files and are not edited. Refer to `main/doc_page_impl_side_panel.md`.

- **Asset store service layer**: Maintains an internal representation of the versioned objects in a store, like a small object storage, kept in sync with the development server, so that a document refers to an object by a short reference block instead of inline data. Its folders belong to the doc pages the page loads (included ones too), each naming them by source path in its `.doc-page/asset.yaml` or using its default `asset/` folder. Provides versions and head, save modes, locks, dependencies, an asset panel for browsing / previewing / reverting, moving inline block data into the store, and a read-only snapshot for builds. Refer to `main/doc_page_impl_asset.md`.

- **Service layer (app and infra services, the service runtime kernel)**: For things that run and keep their own state, unlike assets which are data. Two kinds of services share one mechanism of templates (listed, never run) and instances (a copy of a template, run by a backend of its own): app services serve documents through dashboards and are meant to be stateless, infra services (storage, logging, connections) serve other services and are reached by name. One service registry holds both kinds, found in the built-in folder of the package, in the convention folders of every loaded doc page, and in plain folders of the backend config. The service runtime kernel maintains the registry, routes every infra name to its current instance, provisions an infra instance from a template when a name is required and nobody provides it, starts instances once their required infra is available, runs lifecycle hooks with timeouts, computes dependency status and health, and logs into the built-in logging infra service (queried by principal and feature). Components and panels reach the backend only through `DocServiceStore` (events for dashboards), which alone holds its address, so they work the same wherever the page and the backend run. Provides the built-in infra services (sqlite: a database per consumer with versions, checkout, export and restore; local-backup: a consumer's data as zip files in one local folder, listed from the folder alone, with orphans of deleted instances shown and removed from the page; logging), dashboards placed in documents, and the Services tab (templates and instances by kind, the infra routing table, dependencies, hooks, logs, the config dashboard of an instance). Refer to `main/doc_page_impl_service.md` (the entry: concepts and folders), which points to `doc_page_impl_service_backend.md`, `doc_page_impl_service_kernel.md`, `doc_page_impl_service_storage.md` and `doc_page_impl_service_dashboard.md`.

- **Object service layer (object registry, type registry, object search)**: One model for the documents and the services: the service layers of the page (the doc page source: doc pages, folders, documents, sections, id'd blocks, groups written in documents; the links, from the link index; the asset store) and the service instances (their templates' `typeList` / `objectProvide` / `compList` / `requireList`; the kernel provides every instance, template and instance config) provide objects of types (a DAG, built-in in one JSON file shared with the kernel), with relations (members, containment, links). A registry on the page and one in the kernel discover (federated queries with completeness), resolve (with a status: found, registered, missing, unavailable, unknown), read and update through the provider, cache per provider and accept registrations, never keeping the objects. Views are components exposing `objectView`; `ObjectView`, `ObjectList`, `ObjectGroup` place objects in documents and card diagrams. Provides a search by words in any order (a name, a host, an id, a type; `type:` `in:` `id:` `ns:`), moderated by a plan per provider, a preflight count and a bounded fetch, as an api (`object/search`), a panel (`ObjectSearchPanel`, `ObjectSearch`) and the create panel of a card diagram. Refer to `main/doc_page_impl_obj.md`, and `main/doc_page_impl_obj_search.md` for the search.

- **Event layer**: The one channel by which a component asks the page for something (navigate, edit, resolve a tag, read an asset ...) through `onEvent`, routed to the owning store, with a uniform response; and the other direction, an event the page delivers to the components at a place of a document (a block), which they subscribe to with one hook. Refer to `main/doc_page_impl_event.md`.

- **Component state service layer**: Keeps the state a component has while shown (selection, draft, open folders) outside the component, so it survives navigating away and back and is shared by every rendering of the same block. Refer to `main/doc_page_impl_mdx_comp_state.md`.

- **MDX document in-place editing**: Edit mode in local dev. Maintains an internal representation of the current document as root-level blocks with their source lines, updated after every write, and edits one block at a time by sending line operations to the source file without reload. Provides the block toolbar and insert menu, the component edit-mode contract, and reusable editing primitives (inline value editing, floating panel, source surface, click-outside handling). Side-panel item in-place editing (renaming a label, moving an item, changing the structure of the tree) is supported by the same layer; refer to `main/doc_page_impl_side_panel.md` for that part. Refer to `main/doc_page_impl_edit.md`.

- **Unified api registry, command palette, keyboard maps**: One registry of every api of the page (an operation with declared parameters, answered within the call), built like the component registry from the package's apis, the apis the doc pages declare in yaml, the host's, and at run time the apis components expose (`expose.apiList`) and the apis of running service instances. Every caller uses one entry (`DocApiStore.call`): the command palette (⇧⌘P / F1, which asks for the parameters of an api in a second step), the keyboard maps (yaml map files: the package's default keys named by `config.yaml`, each doc page's in `.doc-page/hotkey/`, the workspace's named by the workspace file; including one another, stacked like the config layers, resolved at the key press with missing apis passed over), and callers outside the page through the development server (`{base}/__doc-api`: list, context, call), which is how an AI agent reads and writes blocks and records test results. The API tab of the settings panel shows it all. Refer to `main/doc_page_impl_api.md`, `main/doc_page_impl_api_command_palette.md`, `main/doc_page_impl_api_hotkey.md`.

- **Slash mode**: In the source of a paragraph or a list being edited, `/` opens a menu of slash actions, and an action can take a parameter with its own completion (`/link` lists the documents of the workspace and writes the link). Provides a registry of slash actions, built at page start beside the component registry, that service layers add actions to, a callback interface for the parameter of an action, and standard effects (replace the slash text, rewrite the parameter, cancel). Components opt in per block kind (`meta.isEditSlashEnabled`). Refer to `main/doc_page_impl_edit_slash.md`.

- **Block-level operations**: Insert, move, duplicate, delete, copy / move blocks to another place or document, paste text as blocks, and block selection mode. Refer to `main/doc_page_impl_block_ops.md`.

- **Block popup**: Opens any component block in a maximizable dialog with a view / edit switch. Refer to `main/doc_page_impl_popup.md`. What a block-like component must and should do around it (view mode, wheel containment, entering without moving the page, the selection and edit-card patterns of a canvas) is in `main/doc_page_impl_mdx_comp_block.md`.

- **Panel contract**: All dialogs of the page are framed by the host's panel component, and can be made movable, resizable and size-remembered. The host also injects menu and segmented-control components. Refer to `main/doc_page_impl.md#the-panel-contract`.

- **Tag system**: Maintains an internal representation of every tag declared on source rules and side-panel items, queried through a tag service. Displays tags on side-panel items, beside links, in text and in a tag overview. Refer to `main/doc_page_impl_tag.md`.

- **Config system**: Maintains an internal representation of the config values of the page and of components, stacked by level: config layers (the package default, one layer per doc page of the workspace of which only the main doc page's is applied, the workspace's own, the browser) around the document levels (source rules, side panel, frontmatter); more layers can be inserted, and the rule of the stack is that the container decides over what it contains. Read through a config service; the settings panel shows what each layer declares, one tab per layer, and edits the doc page and workspace declarations in place. A component can declare its own keys. Refer to `main/doc_page_impl_config.md`; the doc page folder convention (metadata in `.doc-page/`, a doc page named by its folder, its managed folders for assets, components and services, and the built-in folder of the package, and the packages a workspace imports) is in `main/doc_page_impl_dir.md`.

- **Navigation**: Maintains the current location (route, document, fragment) and its history as the single place to change it from. Provides the link / target grammar, anchors and aliases, back / forward / up, and a navigation channel for hosted indexes. Refer to `main/doc_page_impl_nav.md`.

- **Backlinks**: Maintains the link index of the workspace (every reference every document writes, with its line, block, headings and sentence, scanned on the development server and shipped with the source data, kept per changed document) and inverts it on the page into the backlinks of a document. Provides the Backlinks panel of the right column (beside the page headings and the part index), following a backlink to the reference itself with a navigation focus (the link ringed, a component holding it told to reveal it through the delivered event `placeReveal`), the chip to the place a backlink points at, and the referrers a removal dialog shows. Refer to `main/doc_page_impl_nav_backlink.md`.

- **Packages**: Folders of components and service templates, with documents of their own, that a workspace imports by folder (`packageList`), with the packages they need; their config file and folders have fixed names and nothing is optional. Their components are mounted like a doc page's (ids `{packageName}/{tagName}`), their templates join the service registry (origin `package`), and the Workspace tab draws them above the workspace. Refer to `main/doc_page_impl_package.md`.

- **Component registry and MDX components**: How a component is defined and registered (render, placements, exposed meta / icon / modes / config keys), the comment-marked block form for graceful degradation, data reuse between blocks, rendering markdown inside a component, and the components a doc page carries in its own folder (`comp-mdx/` with `comp.yaml` manifests), mounted into the registry when the doc page is loaded; the components of the packages a workspace imports are mounted the same way. Refer to `main/doc_page_impl_mdx_comp.md`, and `main/doc_page_impl_mdx_li.md` for components inside list items.

- **Multilingual content**: Per-language headings, paragraphs, lists and the multi-lang block, with one language preference across the page. Refer to `main/doc_page_impl_multi-lang.md`.

- **YAML Utils**. For any operations involving YAML file editing, refer to `main/doc_page_impl_yaml_utils.md`. Overwriting YAML file simply by writing serialized yaml is usually not acceptable.
